## 3. Движок указателя

Раздел — только математика и обработка сигнала: как из IMU получается точка на экране монитора, что наблюдается, а что принципиально не наблюдается, и как это разложено по уровням L0–L3. Транспорт, инъекция ввода и UI-навигация — в других разделах.

### 3.1 Модель: луч, пивот, плоскость экрана

Система монитора `M`: начало в центре экрана, `x` вправо, `y` вверх, `z` наружу к пользователю. Экран — плоскость `z = 0`, `1920×1080`, масштаб `S_px = 1920/W_м`; для дистанции `0.6 м` это `3200 px/м` и `1° ≈ 33 px` — рабочие числа всех оценок ниже. Система устройства `D`: `y` вдоль длинной оси к верхнему торцу. Ориентация — кватернион `q` из `TYPE_GAME_ROTATION_VECTOR`, матрица `R(q)`.

**Луч.** Выходит из середины верхнего торца телефона, направление — длинная ось, в `D` это `e_y`:

```
d = R(q)·e_y,   |d| = 1
```
**Пивот.** Точка `p = (p_x, p_y, p_z)` в `M`, вокруг которой телефон реально вращается: запястье или локоть, а не торец. Торец смещён от пивота на постоянный вектор `r_0`, поэтому линия луча задаётся парой `(p, d)`, а `r_0` на геометрию не влияет — модели достаточно одного пивота. Допущение модели: **`p` постоянно в течение сессии наведения**; пользователь калибруется в одной стойке и не переносит локоть между касаниями. Это допущение — источник всей ошибки L0 и предмет перецентровки в 3.5.

**Пересечение с плоскостью экрана.** Луч `X(t) = p + t·d`, `t ≥ 0`; условие `p_z + t·d_z = 0`:

```
k = t = −p_z / d_z
u = p_x + k·d_x = p_x − p_z·d_x/d_z
v = p_y + k·d_y = p_y − p_z·d_y/d_z
u_px = (u + W_м/2)·S_px,     v_px = (H_м/2 − v)·S_px
```
Требуется `d_z ≠ 0` и `k > 0`. При `|d_z| < 0.05` точка попадания уходит в бесконечность (луч скользит по плоскости) — отсчёт отбрасывается; при `d_z > 0` луч смотрит от экрана — курсор замораживается на последней валидной точке. Точка попадания зависит только от `p` и `d`: ни дистанция, ни размер экрана не входят отдельными параметрами, они уже внутри `p_z` и масштаба. Именно поэтому всё отображение сворачивается в гомографию с 8 параметрами (3.3).

### 3.2 Почему IMU не даёт позицию

Здесь фиксируется граница возможностей; дальше по документу нигде не утверждается, что положение телефона в комнате определяется по IMU.

**Что даёт IMU.** `TYPE_GAME_ROTATION_VECTOR` — ориентацию (3 угла), акселерометр — вектор удельной силы `g + a`, гироскоп — угловую скорость. Позиции нет ни в одном: акселерометр измеряет **гравитацию**, а не перемещение.

**Что ломается при двойном интегрировании.** Ошибка ориентации `1°` даёт протечку гравитации в горизонтальные оси:

```
a_err = g·sin(1°) = 9.81·0.01745 ≈ 0.17 м/с²
x_err(t) = ½·a_err·t²:   t=1 с → 0.085 м ≈ 8 см;   t=2 с → 0.342 м ≈ 34 см;   t=5 с → 2.1 м
```
Числа брифа (8 см за 1 с, 34 см за 2 с) воспроизводятся этой формулой точно. Постоянное смещение гироскопа `b` (бытовые MEMS: `0.05–0.2 °/с`) даёт линейно растущую ошибку наклона, а значит кубический рост позиции `x_err ≈ ⅙·g·b·t³` — метры на горизонте 10 с.

**Почему фильтры не спасают.** Mahony/Madgwick/комплементарный/EKF пересчитывают только **ориентацию**, смешивая гироскоп с гравитацией. Наблюдения позиции в системе нет вообще, поэтому фильтр её не создаёт. Смещение ускорения он сохраняет: при неизвестном линейном ускорении `g` и `g + a` неразличимы — это фундаментальная ненаблюдаемость, а не дефект реализации. ZUPT (3.10) частично лечит накопление скорости, но координаты не даёт.

**Масштаб ненаблюдаем при чистом вращении.** Если телефон только поворачивается, показания датчиков не зависят от расстояния до экрана, поэтому `p_z` измерить нельзя: «метрический 3D-объём» из IMU не строится. Барометр тоже не помогает: точность `±10–100 см`, у ПК нет отсчёта высоты, и высота вообще не входит в `k = −p_z/d_z` — в пересечение луча с плоскостью входит глубина, а не абсолютная высота.

**Итог, который повторяется в UI и в текстах приложения:** IMU даёт направление луча, не позицию. Абсолютная точка появляется только из (а) калибровки четырьмя касаниями в фиксированной стойке (L0), (б) перецентровки касанием (L1), (в) внешнего наблюдения камерой (L2). Всё остальное — относительное движение курсора, где абсолютная точка не определена by design.

### 3.3 Уровень L0: гомография, 8 параметров, 4 касания

**Почему отображение «направление → экран» — гомография ровно с 8 параметрами.** Из 3.1:

```
u = p_x − p_z·d_x/d_z,   v = p_y − p_z·d_y/d_z
[u, v, 1]ᵀ ~ [ p_x·d_z − p_z·d_x ,  p_y·d_z − p_z·d_y ,  d_z ]ᵀ
```
Правая часть **линейна** по `(d_x, d_y, d_z)`, значит `d ↦ (u,v)` — проективное преобразование плоскости, в которой живёт `d`, то есть гомография `H` 3×3 с точностью до масштаба. Фиксация `h_33 = 1` оставляет **8 свободных параметров**:

```
        ⎡ h1  h2  h3 ⎤
H  =    ⎢ h4  h5  h6 ⎥ ,    (u, v) = (X/W, Y/W),   [X Y W]ᵀ = H·d
        ⎣ h7  h8  1  ⎦
```
Эти параметры вбирают пивот `p` (3), масштаб px/м и размер экрана (1), смещение начала координат экрана (2) и постоянную ошибку выставления осей устройства относительно луча (2). Апостериорно `p_x = h3`, `p_y = h6`, `p_z = −h1 = −h5` для идеального случая, но код на эту интерпретацию не опирается.

**Почему 4 касания дают точное решение.** Одно соответствие «луч `d_i` → пиксель `(u_i, v_i)`» даёт два линейных уравнения на 8 неизвестных. Четыре угла монитора — 8 уравнений: система квадратная, при невырожденных направлениях решение **единственное**, резидуум нулевой с точностью до float. Невырожденность = никакие три из четырёх направлений не лежат в одной плоскости через начало координат, то есть телефон смотрит на экран не строго «в лоб» с нулевым разбросом.

**DLT.** Домножением `u = X/W`, `v = Y/W` на знаменатель:

```
u_i·(h7·dx_i + h8·dy_i + dz_i) = h1·dx_i + h2·dy_i + h3
v_i·(h7·dx_i + h8·dy_i + dz_i) = h4·dx_i + h5·dy_i + h6
A[2i]   = [ dx, dy, dz,  0,  0,  0, −u·dx, −u·dy ]    b[2i]   = u·dz
A[2i+1] = [ 0,  0,  0,  dx, dy, dz, −v·dx, −v·dy ]    b[2i+1] = v·dz
```
Решение — метод Гаусса с выбором ведущего элемента по столбцу: прямой ход к верхнетреугольному виду, обратный ход для `h1..h8`. Обусловленность контролируется по `|a_kk|`: если ведущий элемент `< 1e-6`, калибровка бракуется (касались не четырёх разных углов).

**Резидуум.** Для каждого касания — евклидова ошибка предсказания в пикселях, `RMS = sqrt((1/4)·Σ res_i²)`. Матрица 8×8 не имеет степеней свободы, поэтому RMS-резидум равен нулю **тождественно** (проверено: `2e-13 px` при сдвиге пивота на 10 см) — он не является метрикой качества и не отбраковывает калибровку ни при каком сдвиге руки. Контроль качества — НЕ RMS, а `err₅` на контрольной точке в центре: `≤ 5 px` норма, `5–40 px` — предупреждение, `> 40 px` — отказ калибровки. Второй контроль — `p_z` из `H` в диапазоне `0.35–3.0 м`. Левенберг–Марквардт и RANSAC здесь не нужны: уравнения линейные, неизвестных ровно столько же, сколько уравнений.

```kotlin
data class Vec3(val x: Float, val y: Float, val z: Float)
data class Pt(val x: Float, val y: Float)
class Mat3(val m: FloatArray)          // row-major, 9 элементов

/** DLT: 8 уравнений, 8 неизвестных, Гаусс с частичным пивотом. null — вырожденная калибровка. */
fun fitH(pairs: List<Pair<Vec3, Pt>>): Mat3? {
    require(pairs.size == 4) { "L0 requires exactly 4 corner touches" }
    val a = Array(8) { DoubleArray(9) }                  // 8x8 + правая часть в столбце 8
    pairs.forEachIndexed { i, (d, p) ->
        val dx = d.x.toDouble(); val dy = d.y.toDouble(); val dz = d.z.toDouble()
        val u = p.x.toDouble(); val v = p.y.toDouble()
        a[2 * i]     = doubleArrayOf(dx, dy, dz, 0.0, 0.0, 0.0, -u * dx, -u * dy, u * dz)
        a[2 * i + 1] = doubleArrayOf(0.0, 0.0, 0.0, dx, dy, dz, -v * dx, -v * dy, v * dz)
    }
    for (col in 0 until 8) {                              // прямой ход
        var piv = col
        for (r in col + 1 until 8) if (abs(a[r][col]) > abs(a[piv][col])) piv = r
        if (abs(a[piv][col]) < 1e-6) return null          // плохая обусловленность
        val tmp = a[col]; a[col] = a[piv]; a[piv] = tmp
        for (r in col + 1 until 8) {
            val f = a[r][col] / a[col][col]
            for (c in col..8) a[r][c] -= f * a[col][c]
        }
    }
    val h = DoubleArray(8)                                // обратный ход
    for (r in 7 downTo 0) {
        var s = a[r][8]
        for (c in r + 1 until 8) s -= a[r][c] * h[c]
        h[r] = s / a[r][r]
    }
    return Mat3(floatArrayOf(h[0].toFloat(), h[1].toFloat(), h[2].toFloat(),
        h[3].toFloat(), h[4].toFloat(), h[5].toFloat(), h[6].toFloat(), h[7].toFloat(), 1f))
}

/** Точка попадания в пикселях. null — луч скользит по плоскости (|W| мал). */
fun applyH(h: Mat3, d: Vec3): Pt? {
    val w = h.m[6] * d.x + h.m[7] * d.y + h.m[8] * d.z
    if (abs(w) < 1e-4f) return null
    val x = (h.m[0] * d.x + h.m[1] * d.y + h.m[2] * d.z) / w
    val y = (h.m[3] * d.x + h.m[4] * d.y + h.m[5] * d.z) / w
    return Pt(x, y)
}

fun residualRms(h: Mat3, pairs: List<Pair<Vec3, Pt>>): Float {
    var acc = 0f
    for ((d, p) in pairs) {
        val q = applyH(h, d) ?: return Float.MAX_VALUE
        acc += (q.x - p.x) * (q.x - p.x) + (q.y - p.y) * (q.y - p.y)
    }
    return sqrt(acc / pairs.size)
}
```
### 3.4 Протокол калибровки (сценарий L0)

**Цель.** Получить `H` из четырёх касаний углов и проверить его на независимой точке: калибровка — это **четыре угла + контрольная точка в центре**, а не «четыре касания».

| Требование к стойке | Как проверяется | Почему |
|---|---|---|
| Дистанция ≈ `0.6 м` | `p_z` из `H` в допуске `0.35–3.0 м` | при `p_z` > 1.5 м точность падает пропорционально, вне диапазона модель неприменима |
| Локоть опирается, стойка как при работе | рост `Δd` между шагами | пивот должен быть неподвижен |
| Виден весь экран целиком; телефон не заслоняет угол | углы мишени видны глазом и рукой | иначе касание угла = промах |
| Без переноса руки между касаниями | пауза ≥ 300 мс, контроль `Δd` | сдвиг 5 см → 160 px промаха |

**Пошаговый UX-сценарий.** Порядок касаний фиксирован: **ЛВ → ПВ → ПН → ЛН** (по часовой стрелке от левого верхнего). Порядок задан, потому что по нему проверяется, не зеркалит ли пользователь экран.

| Шаг | Что видит пользователь | Что делает система |
|---|---|---|
| 0 | «Встаньте как обычно, телефон на 0.6 м, локоть на столе» | ждёт покоя 500 мс, калибрует смещение гироскопа (3.7) |
| 1 | Мишень в левом верхнем углу, счётчик «1/4» | по `ACTION_DOWN` берёт IMU-отсчёт с меткой времени, ближайшей к событию касания |
| 2 | Мишень в правом верхнем, «2/4» | то же, проверяет `Δd₁₂ > 2°` |
| 3 | Мишень в правом нижнем, «3/4» | то же |
| 4 | Мишень в левом нижнем, «4/4» | то же, затем `fitH` |
| 5 | Перекрестие в центре, «коснитесь центра» | контрольная точка (валидация) |

**Почему отсчёт берётся по моменту касания, а не «текущий».** Пользователь сначала наводит телефон, затем тянется пальцем: за 150–300 мс палец поворачивает корпус на 1–2°, это 33–66 px ошибки. Касание привязывается к `event.eventTime`, берётся IMU-отсчёт в окне `±10 мс` от этой метки.

**Валидация на контрольной точке.** Пятое касание — центр экрана; предсказание сравнивается с фактом:

```
err₅ = ‖ applyH(H, d₅) − (u₅, v₅) ‖₂
err₅ ≤ 5 px           → принято, H сохраняется
5 px < err₅ ≤ 40 px   → «почти», предложить одну повторную попытку, старый H сохранить
err₅ > 40 px          → провал: H не сохраняется, разбор причины
```
Порог 5 px — меньше половины системного курсора и соответствует ошибке ориентации `0.15°`, то есть пределу точности сенсора. Порог 40 px — граница, за которой промах виден глазом как «курсор мимо кнопки». Шаг 5 — валидация, а не украшение процедуры: **без контрольной точки `H` считается невалидной**, `err₅` не бывает «по умолчанию хорошим».

**Проектор и стена.** Процедура та же: касаться надо поверхности в точке спроецированного угла, а не края полотна или рамки. keystone-искажение прямоугольником не является — в этом случае `H` остаётся валидной (гомография прямоугольника не предполагает), но контрольная точка в центре может дать `err₅` больше нормы; тогда калибровка принимается с предупреждением, а магнетизм включается принудительно.

| Симптом | Причина | Сообщение |
|---|---|---|
| `fitH == null` | касались не четырёх разных углов | «наведите на угол, а не в центр» |
| `RMS` заметно > 0 (не должно случаться) | рука сдвинулась между касаниями, но матрица всё равно квадратная | «не переносите локоть, начните заново» |
| `err₅` велик, `p_z` в норме | нарушен порядок касаний / зеркальный экран | «касайтесь по часовой стрелке, начиная с левого верхнего» |
| `p_z` вне `0.35–3.0 м` | телефон слишком близко или далеко | «отодвиньтесь на вытянутую руку» |
| `Δd < 2°` на шаге | пользователь касался, не наводя | «сначала наведите телефон на мишень» |

**Таймауты и повторы.** 8 с на касание (иначе шаг начинается заново с той же мишенью), 90 с на всю калибровку (после — предложение продолжить в режиме трекпада: бесконечный цикл калибровки хуже её отсутствия), не более 3 полных попыток с паузой 1 с и напоминанием про стойку, отмена в любой момент. `H` хранится в `DataStore` с метаданными: время, `err₅`, `p_z`, разрешение монитора, версия схемы — при смене разрешения или монитора калибровка инвалидируется.

### 3.5 Уровень L1: перецентровка одним касанием

**Утверждение.** Если пивот сместился на `Δ = (Δx, Δy, 0)`, то есть **параллельно** плоскости экрана, точка попадания смещается ровно на `(Δx, Δy)` при любом направлении луча.

**Доказательство.** Пусть `u(d) = p_x − p_z·d_x/d_z`. После сдвига `p' = p + Δ`, причём `p'_z = p_z`:

```
u'(d) = p'_x − p'_z·d_x/d_z = (p_x + Δx) − p_z·d_x/d_z = u(d) + Δx
v'(d) = (p_y + Δy) − p_z·d_y/d_z = v(d) + Δy
```
`Δx`, `Δy` не зависят от `d`: член `p_z·d_x/d_z` сокращается тождественно. Значит сдвиг пивота в плоскости экрана — это параллельный перенос всей картинки, а не деформация. ∎

**Следствие: 2 уравнения на 2 неизвестных.** Пользователь навёл луч на точку с известными пиксельными координатами `(u*, v*)` (якорь) и коснулся экрана телефона. Известны `d` (IMU) и предсказание модели `(u_cal, v_cal) = applyH(H, d)`:

```
Δx = u* − u_cal,    Δy = v* − v_cal
```
Решение точное, полная калибровка не нужна: перецентровка возвращает модель к реальности за время одного тапа.

**Обновление модели.** Поправка вносится композицией с матрицей переноса, `fitH` не пересчитывается:

```
T = ⎡1 0 Δx⎤        H ← T·H        T·H·d = [X + Δx·W, Y + Δy·W, W]ᵀ  ⇒  u' = u + Δx
    ⎢0 1 Δy⎥
    ⎣0 0 1 ⎦
```
```kotlin
/** L1: одна точка-якорь с известными пиксельными координатами. */
fun recenter(h: Mat3, d: Vec3, anchor: Pt): Mat3? {
    val cur = applyH(h, d) ?: return null
    val dx = anchor.x - cur.x
    val dy = anchor.y - cur.y
    if (hypot(dx, dy) > 600f) return null        // защита от грубого промаха или чужого якоря
    val t = Mat3(floatArrayOf(1f, 0f, dx, 0f, 1f, dy, 0f, 0f, 1f))
    return mul(t, h)
}
```
**Поправка в протоколе.** Поправка передаётся как `dpx`, `dpy` — `int16` (`±32767 px`), поэтому сдвиг до 600 px выражается штатно и с запасом. Если `|поправка| > 600 px` — это уже не перецентровка, а новая калибровка: приложение обязано предложить полную процедуру 3.4, а не молча сдвигать картинку. Владелец `H` — **телефон**; агент `H` не считает и хранит только последнюю принятую точку `mouse_abs` (нужна, чтобы нарисовать якорь).

**Границы применимости.** Доказательство требует `Δz = 0`. Если пивот сместился и по глубине, остаётся ошибка `−Δz·(d_x/d_z)`, зависящая от направления: при `Δz = 5 см` и `d_x/d_z ≈ 0.35` (край экрана) это `1.75 см ≈ 56 px`, в центре — ноль. Правило UX: **перецентровка лечит сдвиг вдоль экрана, но не смену стойки**; смена стойки требует L0 заново или L2.

**Жест.** (1) Агент рисует оверлей-метку в известных пиксельных координатах — центр активного окна либо свободный угол экрана. (2) Пользователь наводит телефон на метку; точность курсора не важна. (3) Двойной тап по экрану телефона (одиночный тап в режиме указателя — клик, поэтому перецентровка именно двойной, он же отменяет клик). (4) Приложение берёт `d` на момент первого тапа, координаты метки — из последнего пакета агента, вызывает `recenter`, показывает «выровнено». Источник якоря зависит от ветки: в ветке A (чистый HID) якорь — **фиксированная метка, известная обеим сторонам** (4 угла + центр, координаты зашиты в приложение и в агент); в ветке B агент присылает пакет `anchor` (`0x21`) — позицию нарисованной им метки.

| Триггер автоматического предложения | Условие | Реакция |
|---|---|---|
| Систематический промах в одну сторону | ≥ 3 клика мимо UI-элемента в одном направлении за 5 с | баннер «выровнять одним касанием» |
| Пользователь сам поправил курсор | агент видит смещение, которое не инжектировал | то же, не чаще раза в 20 с |
| Долгий простой | > 30 с без событий ввода | тихое предложение при следующем наведении |
| Телефон поднимали | всплеск акселерометра, затем покой | предложение до первого клика |
| После реконнекта | `handshake → active` | всегда: пивот мог измениться |

Автоматически, без подтверждения, перецентровка **не применяется**: неверный якорь сдвинет модель на сотни пикселей и будет выглядеть как поломка. Предлагать — всегда, применять — только по подтверждённому касанию.

### 3.6 Относительный и абсолютный режимы

| | **Абсолютный (L0/L1/L2)** | **Относительный (IMU → скорость)** |
|---|---|---|
| Что передаётся | координаты точки попадания | приращения `Δx, Δy` |
| Калибровка | нужна (четыре угла + контрольная точка в центре) | не нужна |
| Абсолютная точка определена | да, до первого сдвига руки | нет, by design |
| Ощущение | «указка»: куда навёл — там курсор | «мышь в воздухе»: курсор тянется за поворотом |
| Сдвиг руки 5 см | промах 160 px, лечится перецентровкой | промаха нет, плывёт точка отсчёта |
| Крупные перемещения | точно и сразу, весь экран за `≈ 58°` поворота | много поворотов, нужен «подъём» (clutch) |
| Доводка 1–5 px | шумно: дрожание `0.1° ≈ 3 px` | хорошо с deadzone и One Euro |
| BIOS/UAC/игры | только при absolute HID-устройстве | да, обычные relative-дельты |
| Требования | стабильная стойка, свет (L2), разрешение | покой в начале, повторная центровка |

**Отличие по ощущениям.** Абсолютный режим экономит движения: экран 1920 px при `1° ≈ 33 px` покрывается поворотом кисти на `58°`. Относительный требует «перехватов», как мышь на маленьком коврике: повернул на 30°, поднял, вернул руку.

**Mouse acceleration Windows.** В относительном режиме ОС применяет свою кривую («Enhanced pointer precision», параметры `SPI_GETMOUSE`: `threshold1`, `threshold2`, `accel`), и она перемножается с нашей кривой из 3.7 — двойное усиление, ощущение «резины». Порядок решений: (1) агент на время сессии указателя ставит `accel = 0` через `SPI_SETMOUSE` и возвращает прежние значения при выходе; (2) агент инжектирует дельты ниже `threshold1`, где системная кривая почти линейна; (3) в режиме A акселерацию отключает пользователь, приложение даёт инструкцию и предупреждение.

**Абсолютный путь через HID-digitizer.** В режиме A абсолютные координаты возможны, если телефон регистрирует дополнительный HID-интерфейс класса digitizer (Usage Page `0x0D`) с логическими границами `0..32767`. Windows примет его как абсолютный указатель и сама отмасштабирует в `0..65535`; акселерация к абсолютным событиям не применяется. Ограничения: конфликт с перьевым/сенсорным стеком (лишние контакты в raw input, кольца касаний), часть OEM-прошивок BT-стека не отдаёт произвольные HID-отчёты, композит требует ручной сборки report descriptor. Поэтому в v1 абсолютный режим в ветке A работает **только** через дополнительный HID-интерфейс digitizer (экспериментальный флаг, по умолчанию выключен); в ветке B — пакетом `mouse_abs` (`0x07`): координаты в пикселях и инъекция `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK` с нормализацией в `0..65535`. Если digitizer отключён, а агента нет — указка работает в относительном режиме, и это надо сказать пользователю в интерфейсе, а не молча. Переключение режимов мгновенное; при входе в абсолютный режим без валидной `H` показывается калибровка, а не прыжок курсора в угол.

### 3.7 Фильтрация и обработка сигнала

Конвейер на каждый отсчёт IMU (100–200 Гц): `raw gyro → bias-коррекция → deadzone → One Euro → кривая ускорения → H·d (или Δ курсора) → пакет`.

**One Euro filter.** Обычный ФНЧ вынуждает выбирать между дрожанием и лагом. One Euro делает cutoff зависимым от скорости: медленно — сильная фильтрация, быстро — слабая. На одну ось (`x` — угол в градусах, `Te` — период):

```
tau(fc)   = 1/(2π·fc)
alpha(fc) = 1/(1 + tau(fc)/Te)
dx_raw    = (x_k − x_{k−1})/Te
dx_hat    = LPF(dx_raw, alpha(dCutoff))
fc        = minCutoff + beta·|dx_hat|
x_hat     = LPF(x_k, alpha(fc)),      LPF(v,a) = a·v + (1−a)·v_prev
```
Профилей два, оба — тот же фильтр с разными параметрами; профиль переключается в настройках:

```
fast (по умолчанию):  minCutoff = 4.0 Гц, beta = 0.02,   dCutoff = 1.0 Гц
precise (опция):      minCutoff = 1.0 Гц, beta = 0.007,  dCutoff = 1.0 Гц
τ = 1/(2π·fc)
```

**fast** — `τ ≈ 40 мс` в покое и `≈ 30 мс` при `60 °/с`; ошибка наведения при `1° ≈ 33 px` — доли пикселя, лаг на быстром движении не заметен. **precise** — `τ ≈ 159 мс` в покое и `≈ 94 мс` при `100 °/с`: для наведения непригодно (пользователь видит «резину»), применяется только для точной доводки по уже выбранному элементу. Величина `τ` — это **групповая задержка** профиля, она складывается с бюджетом отдельно; `~2 мс` — стоимость CPU на отсчёт, а не задержка, поэтому «фильтр стоит 2 мс и влезает в 25 мс» — неверная арифметика.

```kotlin
class OneEuro(var minCutoff: Double = 4.0, var beta: Double = 0.02,
              val dCutoff: Double = 1.0) {
    private var xPrev = Double.NaN; private var dxPrev = 0.0
    private fun alpha(cutoff: Double, te: Double) = 1.0 / (1.0 + (1.0 / (2.0 * PI * cutoff)) / te)
    fun filter(x: Double, te: Double): Double {
        if (xPrev.isNaN()) { xPrev = x; return x }
        val dx = (x - xPrev) / te
        val aD = alpha(dCutoff, te)
        val dxHat = aD * dx + (1 - aD) * dxPrev
        val a = alpha(minCutoff + beta * abs(dxHat), te)
        val xHat = a * x + (1 - a) * xPrev
        xPrev = xHat; dxPrev = dxHat
        return xHat
    }
}
```
Фильтруются **углы**, а не пиксели: пиксельный фильтр зависит от масштаба и ведёт себя по-разному на разных дистанциях. Один экземпляр на ось, `te` — из фактических меток `SensorEvent.timestamp`, а не из номинальной частоты: иначе при просадке частоты фильтр врёт.

**Deadzone.** После фильтра остаётся смещение гироскопа, курсор «ползёт» на 1–3 px/с. Мёртвая зона применяется к **модулю** углового вектора, не по осям (поосевая зона съедает медленные диагонали): `|ω| < 0.5 °/с → ω := 0` (это `≈ 16 px/с`). Порог адаптивный: после 2 с неподвижности — `0.8 °/с` (дрожание уставшей руки растёт), при начале движения — мгновенно `0.5 °/с`.

**Кривая ускорения** (относительный режим, «медленно = точно, быстро = далеко»): `v_out = ω·gain(|ω|)`,
`gain = 1 + a·k·(|ω|/ω_ref)^1.5`, где `k = 6`, `ω_ref = 40 °/с`, `a` — пользовательская настройка
`acceleration` (по умолчанию 0.35, диапазон 0–1: 0 = линейный курсор, 1 = максимальное ускорение).

| ω, °/с | 5 | 40 | 100 |
|---|---|---|---|
| gain при `a = 0.35` | 1.09 | 3.1 | 9.3 |
| Смысл | доводка по пикселям | обычное наведение | бросок через экран |

Показатель 1.5, а не 2: при квадратичной кривой мелкие движения «вязкие», при линейной быстрые броски не долетают. Кривая живёт в приложении; системная акселерация отключена (3.6), иначе усиления перемножаются.

**Частота регистрации.** `SENSOR_DELAY_GAME` — это ~50 Гц, 20 мс на отсчёт: в бюджете 25 мс без фильтра (сенсор → курсор) такой отсчёт съедает весь запас и даёт ступенчатое движение. Рабочий диапазон — **100–200 Гц** (`SENSOR_DELAY_FASTEST` либо явный `samplingPeriodUs = 5000..10000`). Выше 200 Гц на Android 12+ требуется `HIGH_SAMPLING_RATE_SENSORS` в манифесте, без него система молча режет частоту. Выше 200 Гц смысла нет: транспорт отдаёт 60–120 Гц.

**Почему `TYPE_GAME_ROTATION_VECTOR`, а не `ROTATION_VECTOR`.** Обычный rotation vector использует магнитометр и строит абсолютный курс; рядом с монитором, колонками и металлическим столом поле искажено — курс прыгает на 5–20°, компас сбивается о железо. `GAME_ROTATION_VECTOR` использует только гироскоп и акселерометр: магнитных артефактов нет, плата — медленный дрейф курса (`0.5–2 °/мин` у бытовых MEMS), то есть сползание картинки на 15–60 px/мин. Это лечится перецентровкой (3.5), а не «более умным фильтром»; подмешивание магнитометра ради нулевого дрейфа в реальной комнате даёт худший результат.

**Калибровка смещения гироскопа при старте.** `bias` — постоянная добавка к угловой скорости, у MEMS ещё и температурозависимая (`0.01–0.05 °/с` на 10 °C). Процедура: (1) телефон неподвижен 1–1.5 с; (2) условие валидности `|ω| < 0.5 °/с`, `‖a‖ ∈ [9.5, 10.1] м/с²`, разброс по осям `< 0.05 м/с²`; (3) `bias = среднее(ω)` по окну, вычитается из всех отсчётов; (4) пока условие не выполнено, указатель не активируется («держите телефон неподвижно»), иначе первая калибровка уедет на 2–5°; (5) перекалибровка при росте температуры на `> 5 °C` и при возврате из фона.

### 3.8 Крен и его (не)влияние

Крен — вращение телефона вокруг собственного луча. Луч `d = R(q)·e_y`, а поворот вокруг оси `d` даёт `R_roll(φ)·d = d` для любого `φ`: **крен не меняет направление луча и не двигает точку попадания** ни в одном режиме абсолютного наведения. Следствия: в L0/L1/L2 крен не калибруется, индикатор «ровно держите» не нужен, вращение телефона вокруг луча — свободное действие. Крен влияет только на разложение углов по осям в относительном режиме: если считать `pitch/yaw` в системе устройства, при крене 45° горизонтальный поворот руки поведёт курсор по диагонали. Поэтому приращения берутся из `d_x`, `d_y` (нормированных на `d_z`) в системе монитора, а не из углов Эйлера устройства. Виден крен пользователю только в жестах свайпа и экранной клавиатуре в руке — к наведению это не относится.
### 3.9 Уровень L2: ARCore, VIO и поза монитора

**Идея.** На L0/L1 позиция пивота — догадка, устаревающая при движении руки. На L2 она наблюдается: VIO даёт 6DoF-позу телефона в мире ARCore, поза монитора получается из распознанного изображения, пивот из модели исчезает.

**Как получается поза монитора.** (1) ПК-агент выводит на монитор калибровочное изображение с известными пиксельными координатами углов — полноэкранно либо компактный маркер в углу, чтобы не мешать работе; годится и напечатанная наклейка известного размера. (2) `Augmented Images` распознаёт изображение из заранее собранной `AugmentedImageDatabase` и возвращает позу: поворот и перенос относительно мира ARCore. База собирается из `assets/ar/` (файл образа + ширина в метрах); отдельного экрана создания базы в v1 нет — образ фиксированный. (3) По соответствию углов маркера пикселям монитора получается плоскость монитора в мире: базис `(e_u, e_v)`, начало, нормаль `n`. Метрический масштаб берётся из физического размера маркера, а если он неизвестен — из EDID (`GetDeviceCaps(HORZSIZE/VERTSIZE)`), с ручным вводом диагонали как fallback (EDID врёт на проекторах и дешёвых панелях).

**Что это даёт.** Касание на экране телефона — пиксель `(x_t, y_t)`, то есть луч в системе камеры (интринсики известны). Поза телефона переводит луч в мир, пересечение с плоскостью монитора даёт 3D-точку, проекция по базису — пиксель экрана:

```
X(λ) = T_phone · ray_camera(x_t, y_t)
λ*   = −( n·(O − P_plane) ) / ( n·D )
pixel = ( (X* − P_plane)·e_u · S_px ,  (X* − P_plane)·e_v · S_px )
```
Это **метрический PnP**: и положение телефона, и плоскость экрана наблюдаются, поэтому трансляция руки — не ошибка, а измерение. Отсюда главное свойство L2: промах при сдвиге руки **не растёт** — 5, 10 и 14 см дают один и тот же результат (в демо 0 px), потому что пивот исключён из модели, а не «скомпенсирован».

**Смена дистанции до экрана.** На L0/L1 `p_z` — константа модели, поэтому изменение дистанции на 20 % (встал → сел) даёт ошибку до 240 px у правого края и 275 px в углу. L1 это **не лечит**: доказательство 3.5 требует `Δz = 0`, а здесь `Δz ≠ 0`. Лечится перекалибровкой по порогу `p_z` 15 % (приложение требует её само) или уровнем L2, где дистанция наблюдается.

| Ограничение | Проявление | Что делаем |
|---|---|---|
| Нужен свет | в темноте VIO теряет трекинг | подсветка экрана телефона, деградация до L0 |
| Нужны текстуры | однотонные стены и стол → потеря | подсветка маркера, деградация |
| Маркер должен быть виден | рука или кружка перекрыла → поза устарела | повторное распознавание, кэш позы 10 с |
| Расход и нагрев | камера + VIO ≈ 1.5–3 Вт, троттлинг через 10–20 мин | ниже частота кадров, отключение VIO при простое |
| Поддержка устройств | ARCore не на всех моделях | проверка при старте, иначе только L0/L1 |
| Дрейф VIO | 1–2 % пути, рывки при быстром движении | слияние с IMU, ZUPT (3.10) |

**Деградация до L0.** `TrackingState` в `PAUSED`/`STOPPED` — штатное состояние, а не ошибка: курсор фиксируется на последней валидной точке, в статусе «нет трекинга». Восстановление в пределах 2 с — работа продолжается; дольше 10 с — автоматический переход на L0 с сохранённой `H` и предложение перецентровки (замороженный курсор недопустим). Обратный переход на L2 — только по явному действию («включить камеру»), чтобы камера не включалась неожиданно.

### 3.10 Уровень L3: ZUPT

**Статус раздела: вне v1 — исследование, в приёмку v1 не входит.** ZUPT (zero velocity update) — обнуление скорости интеграла акселерометра в моменты, когда телефон неподвижен. Это единственный способ получить из IMU хоть какое-то перемещение, и его пределы надо назвать сразу.

**Зачем.** Между двумя перецентровками абсолютная точка неизвестна; интегрирование ускорения могло бы «довести» курсор, но дрейф `½·a_err·t²` (3.2) съедает результат. ZUPT дрейф не убирает, но **не даёт ему накапливаться через паузы**: пока телефон стоит, скорость принудительно равна нулю.

```
still ⇔ | ‖a‖ − g | < 0.3 м/с²  ∧  |ω| < 2 °/с   на всём окне T_still
T_still ∈ [0.3 с ; 0.5 с]
```
Окно 0.3–0.5 с: короче 0.3 с — обычная пауза между микродвижениями руки принимается за покой и режет движение; длиннее 0.5 с — обнуление опаздывает и пользователь видит «доползший» курсор.

```kotlin
enum class Motion { MOVING, STILL_CANDIDATE, STILL }

class Zupt(val windowS: Double = 0.4) {
    private var stillSince = Double.NaN
    private var motion = Motion.MOVING
    var velocity = Vec3(0f, 0f, 0f); private set

    fun update(acc: Vec3, gyroDegS: Float, tSec: Double): Motion {
        val quiet = abs(norm(acc) - 9.81f) < 0.3f && abs(gyroDegS) < 2f
        if (!quiet) { stillSince = Double.NaN; motion = Motion.MOVING; return motion }
        if (stillSince.isNaN()) { stillSince = tSec; motion = Motion.STILL_CANDIDATE }
        if (tSec - stillSince >= windowS) { motion = Motion.STILL; velocity = Vec3(0f, 0f, 0f) }
        return motion
    }
    /** Между ZUPT-событиями: v += (a − g)·dt, затем x += v·dt. */
    fun integrate(accWorld: Vec3, dt: Float): Vec3 {
        velocity = add(velocity, scale(sub(accWorld, Vec3(0f, 0f, 9.81f)), dt))
        return velocity
    }
}
```
**Что даёт.** Ошибка позиции ограничена длительностью **непрерывного** движения, а не всей сессией: 0.5 с дают `½·0.17·0.25 ≈ 2 см`, а не 34 см за 2 с. Курсор перестаёт уползать в паузах — самый заметный дефект чистого интегрирования. Побочно появляется детектор «пользователь остановился»: по нему включается магнит курсора и предлагается перецентровка.

**Чего не даёт (и не будет).**

| Не даёт | Почему |
|---|---|
| Абсолютной координаты | обнуляется скорость, положение остаётся интегралом от неизвестного начала |
| Масштаба | при чистом вращении `p_z` ненаблюдаем (3.2), ZUPT его не восстанавливает |
| Компенсации дрейфа курса | yaw-дрейф — ошибка ориентации, ZUPT её не видит |
| Точности при непрерывном движении | 2 см за 0.5 с движения — это уже ≈ 64 px |
| Замены L2 | камера наблюдает трансляцию, ZUPT предполагает её отсутствие |

Поэтому L3 остаётся **исследованием вне v1** (в приёмку не входит): он сокращает уползание между перецентровками и питает детектор покоя, но абсолютную точку по-прежнему дают только касание (L0/L1) или камера (L2). «Наведение без калибровки на акселерометре» не обещается: числа выше дают 2–5 см ошибки за полсекунды движения.

### 3.11 Ожидаемая точность по уровням

Условия: `1920×1080`, дистанция `0.6 м`, `3200 px/м`, `1° ≈ 33 px`, спокойная рука, исправный сенсор. P50/P90 — ошибка попадания в пикселях по контрольной сетке 3×3.

| Уровень | Режим | P50, px | P90, px | Сдвиг руки 5 / 10 / 14 см | Требования |
|---|---|---|---|---|---|
| **L0** | абсолютный | ограничена `err₅` | — | 160 / 345 / 501 px | калибровка «четыре угла + контрольная точка», стойка не меняется |
| **L1 (без магнетизма)** | абсолютный | ≤ 33 | ≤ 99 | 160 / 345 / 501 px, затем 0 после перецентровки | одно касание якоря на каждое смещение |
| **L1 + магнетизм** | абсолютный | ≤ 16 | ≤ 33 | то же, плюс доводка по цели в радиусе 60 px | якорь и магнетизм, таймаут UIA-провайдера 120 мс |
| **L2 (ARCore)** | абсолютный | — | ≤ 33 | 0 / 0 / 0 px | свет, текстуры, видимый маркер, поддержка ARCore; опция v1.1 |
| **Относительный** | относительный | не нормируется | не нормируется | промаха нет, точка отсчёта не определена | deadzone, One Euro, отключённая акселерация ОС |

Читать так: L0 точен, **пока рука не сдвинулась**; L1 возвращает точность после сдвига за одно касание; L2 снимает зависимость от сдвига вообще, но зависит от света и железа; относительный режим вообще не про абсолютную точку. Никакая комбинация уровней не отменяет физику 3.2: между касаниями абсолютная позиция наблюдается только на L2. Отдельная оговорка: P50/P90 — не пропускная способность, а ошибка попадания; систематическая ошибка (сдвиг стойки) не усредняется по нажатиям, поэтому медиана её не скрывает.

### 3.12 Диагностика

**Лог** (JSON-строки, ротация по 2 МБ, кольцевой буфер 20 файлов):

| Поле | Частота | Зачем |
|---|---|---|
| `sampleTs`, `dt` | каждый отсчёт | ловить просадки частоты: Android режет до 50 Гц незаметно |
| `d`, `pitch/yaw` | каждый отсчёт | воспроизвести траекторию офлайн |
| `hit` / `noHit` | каждый отсчёт | доля отброшенных лучей — индикатор плохой геометрии |
| `err5`, `p_z` (контрольная точка) | калибровка, перецентровка | единственный контроль качества; RMS по четырём точкам не пишется — он тождественно нулевой (3.3) |
| `touches`, шаги, таймауты | на событие | где пользователь застревает |

| `yawDrift` (°/мин) | раз в 10 с | когда предлагать перецентровку |
| `tempC` (батарея/ambient) | раз в 30 с | связать ухудшение с нагревом |
| `level`, `mode`, `transport` | при смене | контекст для любого бага |
| `latencyMs` (сенсор → отправка) | раз в 5 с, гистограмма | контроль бюджета: без фильтра ≤ 25 мс, с фильтром fast P50 ≤ 60 мс |

**Экран диагностики** (из настроек и по долгому нажатию на статус):

- Крупно **точка попадания**: `u, v` и ошибка до контрольной точки, обновление 10 Гц.
- **Контрольная сетка 3×3**: девять мишеней; навёл и нажал «проверить» — рядом с каждой мишенью крестик «предсказано» и «факт» с числом, ниже строка `P50 / P90 / max`.
- **Кнопка «проверить»**: одна контрольная точка в центре; светофор `≤ 5 px` зелёный, `≤ 40 px` жёлтый, больше — красный, с подсказкой из таблицы 3.4.
- Строка уровня: `L0 | L1 | L2` (L3 — вне v1), режим (абсолютный/относительный), «трекинг: ок / потерян», «маркер: виден / нет».

### 3.13 Рассмотренные альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Трилатерация по BLE/UWB-маякам | маяков нет в комплекте с ПК, без AoA точность 10–30 см ≈ 300–900 px, установка убивает работу «из коробки» |
| Свой трекер по сетке экрана без ARCore | те же требования к свету и текстурам плюс собственная реализация VIO — месяцы работы ради того, что ARCore даёт готовым |
| Абсолютный курс по магнитометру | поле искажено монитором и колонками, ошибка 5–20° ≈ 165–660 px |
| Барометр для глубины | точность `±10–100 см`, высота не входит в пересечение луча с `z = 0` |
| Калибровка «наведи на курсор» | истина неизвестна: курсор — наше же предсказание, система вырождается |
| Позиционирование по IMU (двойное интегрирование) | ошибка растёт квадратично: 8 см за 1 с и 34 см за 2 с при ошибке наклона `1°` (3.2); ни один фильтр ориентации не создаёт ненаблюдаемое наблюдение позиции |
