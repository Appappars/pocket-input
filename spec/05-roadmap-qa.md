## 5. Реализация, тесты, риски

Раздел описывает, как проект собирается физически: дерево репозитория, фазы с проверяемым
результатом, задачи первой фазы по zero-decision rule (файл → действие → критерий), три уровня
тестов, матрицу устройств, риски, открытые вопросы заказчику и итоговую смету с буфером.
Все числа взяты из `spec/_brief.md`; ссылки на уровни указателя (L0/L1/L2/L3) — оттуда же.

### 5.1 Структура репозитория

Один репозиторий, три сборочных корня: Android-приложение, ПК-агент, общие артефакты
(proto, docs, tools). Каталог `generated/` — единственное место, где допустима запись
по глобу: имена файлов там создаёт инструмент, а не человек.

```text
pocket-input/
├── android/                                  # Android-приложение, Kotlin + Compose
│   ├── app/src/main/AndroidManifest.xml      # разрешения, foreground service
│   ├── app/src/main/res/                     # строки RU/EN, темы
│   ├── app/src/main/assets/ar/               # образ маркера для Augmented Images
│   ├── app/src/main/kotlin/dev/pocketinput/
│   │   ├── app/                              # Application, DI-контейнер, конфиг сборки
│   │   ├── ui/connect/                       # экран подключения и выбора транспорта
│   │   ├── ui/trackpad/                      # экран трекпада, жесты, скролл
│   │   ├── ui/keyboard/                      # экран клавиатуры, sticky-модификаторы
│   │   ├── ui/pointer/                       # экран указки: калибровка, наведение
│   │   ├── ui/settings/                      # настройки фильтра, чувствительности, темы
│   │   ├── ui/diagnostics/                   # частоты, латентность, лог пакетов
│   │   ├── hid/                              # BluetoothHidDevice: дескрипторы, репорты
│   │   ├── transport/                        # интерфейс Transport и его реализации

│   │   ├── pointer/                          # гомография, One Euro, кривая ускорения
│   │   ├── sensor/                           # подписка на rotation vector, буферизация
│   │   ├── ar/                               # ARCore-сессия и Augmented Images (L2)
│   │   └── service/                          # foreground service, уведомление, wake lock
│   ├── app/src/test/                         # JVM-юнит-тесты (гомография, кодек, фильтр)
│   ├── app/src/androidTest/                  # инструментальные тесты Compose и сенсоров
│   ├── app/build.gradle.kts                  # модуль приложения, sourceSets для proto
│   ├── settings.gradle.kts                   # состав сборки
│   ├── gradle/wrapper/                       # версия Gradle зафиксирована
│   └── gradle/libs.versions.toml             # единственный источник версий зависимостей
├── agent/pocketinput/                        # ПК-агент, Python 3.11+
│   ├── __main__.py                           # точка входа, разбор аргументов, старт трея

│   ├── transport/                            # RFCOMM (socket), BLE GATT (bleak), Wi-Fi TCP
│   ├── inject/                               # SendInput через ctypes, Unicode, clipboard fallback

│   ├── overlay/                              # подсветка цели: прозрачное окно WS_EX_LAYERED

├── agent/pyproject.toml                      # метаданные пакета агента
├── agent/requirements.txt                    # зафиксированные зависимости агента
├── agent/tests/                              # pytest: инъекция (mock), протокол, магнетизм
├── proto/pocketinput_v1.proto                # описание пакетов, единственный источник истины
├── proto/generated/                          # сгенерированный Kotlin/Python-код, не править руками
├── docs/                                     # этот документ, ADR, гайд по калибровке, FAQ
│   ├── adr/                                  # решения с альтернативами и датой

│   ├── calibrate_grid.py                     # генерация сетки 3x3 и сбор P50/P90
│   ├── latency_bench.py                      # 100 проб «сенсор → курсор», CSV на выходе
│   └── hid_probe.py                          # проверка HID-профиля на конкретном телефоне
├── tools/build.ps1                           # единая сборка Windows-артефактов агента
├── .gitignore                                # generated/, build/, локальные замеры

```

Каталог `android/app/src/main/kotlin/.../proto/` содержит только сгенерированный код; источник —
`proto/`.

Генерация кода протокола: `proto/pocketinput_v1.proto` → `tools/gen_proto.py` (protoc 27.x) →
`proto/generated/kotlin/` подключается в `android/app/build.gradle.kts` через `sourceSets`,
`proto/generated/python/` копируется в `agent/pocketinput/proto/`. Ручная правка сгенерированного
кода запрещена.

Правила размещения, чтобы не было «куда положить новый файл»:

| Что | Куда | Почему именно туда |
|---|---|---|
| Новый экран | `android/.../ui/<экран>/` | экраны не смешиваются с логикой |
| Новый пакет протокола | `proto/pocketinput_v1.proto` + регенерация | один источник истины для двух сторон |
| Новая реализация транспорта | `transport/` рядом с существующими | интерфейс `Transport` не меняется |
| Новый алгоритм указателя | `android/.../pointer/` + тест в `app/src/test/` | вся математика тестируется на JVM |
| Новый поставщик прямоугольников | `agent/pocketinput/magnet/` | провайдер за общим интерфейсом |
| Скрипт замера | `tools/` | воспроизводимость полевых тестов |

### 5.2 Фазы

Шесть фаз. Каждая заканчивается состоянием, которое можно показать на реальном ПК и
измерить; фаза не считается закрытой без артефакта в `docs/measurement/`. Каждая фаза
закрывается артефактом `docs/measurement/phaseN-report.md` (N = 0..5) по шаблону фазы 0.

| Фаза | Объём | Что работает в конце фазы | DoD (проверяемо) | Дней |
|---|---|---|---|---|
| **0. Спайк HID** | ~600 строк Kotlin, один экран, без UI-дизайна; объём проверки — минимум 3 телефона × 2 ПК = 6 пар из матрицы 5.5 (цель — 6 пар, а не 15) | Телефон регистрируется как HID-композит (клавиатура+мышь), двигает курсор и печатает латиницу на реальном Windows-ПК | Курсор двигается на 2 ПК из 2 протестированных; латиница вводится в Блокнот; `hid_probe.py` печатает `HID_DEVICE != null`; лог wake-after-idle снят | 5 |
| **1. Трекпад + клавиатура по HID** | ~2500 строк: Compose-экраны, жесты, sticky-модификаторы, foreground service; три задачи с acceptance — ниже под таблицей | Полноценный трекпад (движение, тап, двойной тап, drag, скролл двумя пальцами) и клавиатура с модификаторами, всё через HID | Все три задачи закрыты; сборка запускается без ручных шагов | 12 |
| **2. Протокол, агент и Unicode** | ~1800 строк Kotlin + ~1600 строк Python: proto, FSM, RFCOMM/BLE, трей, инъекция, `text_unicode`, `KEYEVENTF_UNICODE`, clipboard-fallback | Тот же трекпад и клавиатура, но через агент; кириллица, CJK и эмодзи работают; автопереподключение | Round-trip кодек-тест зелёный; кириллица вводится в 3 приложениях; reconnect < 3 с после обрыва | 14 |
| **3. Указка L0 + L1** | ~1500 строк: гомография, калибровка по четырём углам + контрольная точка, перецентровка касанием | Калибровка четырьмя касаниями и контрольной точкой в центре, наведение по экрану, одно касание перецентровывает | Резидуум калибровки < 0.01 px на синтетике; P50 ≤ 33 px на сетке 3x3 при 1920x1080 с 0.6 м | 12 |
| **4. Магнетизм и подсветка** | ~900 строк: UIA/CDP-провайдеры, притяжение, подсветка цели оверлеем | Курсор притягивается к кликабельным элементам в радиусе ~60 px с подсветкой цели | Магнетизм срабатывает на 20/20 кнопках в браузере и 15/15 в нативном приложении; подсветка совпадает с прямоугольником цели; ложных притяжений ≤ 2/35 | 9 |
| **5. ARCore L2 и полировка (v1.1, вне критического пути v1)** | ~1200 строк: ARCore-сессия, Augmented Images, fallback, диагностика, настройки | L2 даёт 6DoF: промах не растёт при сдвиге руки; при отсутствии ARCore — чистый откат на L1 с сообщением | Сдвиг 14 см не даёт промаха > 33 px в L2; откат на L1 проверен на устройстве без ARCore; чек-лист 5.8 закрыт | 13 |

Итого по фазам 0–4 — 52 дня чистой разработки (критический путь v1); фаза 5 (L2) — ещё 13 дней
вне этого пути. С буфером — см. 5.9.

Задачи фазы 1 (каждая закрывается отдельно; «сделано» без acceptance не считается):

1. **Экраны «Подключение», «Трекпад», «Клавиатура» по 4.5** — Compose-экраны с состояниями
   подключения, жестами и клавиатурой, навигация между ними. Acceptance: ручное прохождение
   сценариев 5.4.2 по этим экранам без падений — ни одного краша в `adb logcat` и в отчёте фазы.
2. **Жесты трекпада из 4.6** — движение, тап, двойной тап, drag, скролл двумя пальцами.
   Acceptance: 5 из 5 жестов работают на одном ПК.
3. **Интеграция с 5.3 п. 5–6** — `ConnectScreen` и `TrackpadScreen` на реальном устройстве,
   с реальным HID-подключением. Acceptance: курсор двигается и латиница вводится на 2 ПК.

Unicode-работы (`text_unicode`, `KEYEVENTF_UNICODE`, clipboard-fallback) входят в фазу 2, а не в
фазу 4: иначе DoD фазы 2 требует кириллицы, которой ещё нет.

### 5.3 Задачи фазы 0 (спайк HID)

Фаза 0 отвечает на единственный вопрос, от которого зависит вся архитектура: отдаёт ли
конкретный телефон профиль `HID_DEVICE`. Задачи идут по zero-decision rule: файл, действие,
критерий. Реализацию внутри файла исполнитель не выбирает — она задана.

1. **`android/app/src/main/AndroidManifest.xml`** — добавить `BLUETOOTH_CONNECT`,
   `BLUETOOTH_SCAN`, `POST_NOTIFICATIONS`, объявить foreground service с
   `foregroundServiceType="connectedDevice"`. Проверка: `./gradlew :app:processDebugMainManifest`
   завершается без ошибок, в собранном манифесте присутствуют все три разрешения.
2. **`android/app/src/main/kotlin/.../service/PocketInputService.kt`** — foreground service,
   который стартует при открытии приложения и держит уведомление «PocketInput: подключено/нет».
   Проверка: на Android 13+ уведомление видно, после 30 мин в фоне сервис жив (`adb shell dumpsys activity services` содержит запись).
3. **`android/app/src/main/kotlin/.../hid/Descriptors.kt`** — два массива байт дескрипторов:
   клавиатура (report ID 1, модификаторы + 6 кодов) и мышь (report ID 2, 3 относительные оси
   int8 + 5 кнопок + колесо). Источник дескрипторов —
   `https://github.com/ToxicOrca/ghostboard-android-bluetooth-mouse-keyboard`, файл
   `bluetooth/BluetoothHidManager.kt`; коммит фиксируется в `docs/measurement/phase0-report.md`.
   Массивы байт копируются в `android/.../hid/Descriptors.kt` без изменений.
   Проверка: unit-тест проверяет длину массивов и что байт `0x05, 0x01` (Usage Page Generic Desktop)
   присутствует в обоих; ПК в диспетчере устройств показывает «HID-совместимая мышь» и «Клавиатура HID».
4. **`android/app/src/main/kotlin/.../hid/HidTransport.kt`** — регистрация через
   `BluetoothHidDevice.registerApp`, метод `sendReport(reportId, bytes)`, обработка
   `onGetReport`/`onSetReport` заглушками. Регистрация — ОДИН вызов `registerApp` с составным
   дескриптором, где клавиатура имеет report ID 1, мышь — report ID 2; отправка идёт через
   `sendReport(1, …)` / `sendReport(2, …)`. Проверка: `getProfileProxy(..., HID_DEVICE)` не null
   на 2 из 3 устройств матрицы (5.5); лог содержит `registered`, `connected`.
5. **`android/app/src/main/kotlin/.../ui/connect/ConnectScreen.kt`** — список спаренных устройств,
   кнопка «Подключить», текст ошибки при `null`-профиле: «Телефон не поддерживает HID; нужен агент».
   Проверка: ручной прогон — на телефоне без профиля показывается именно этот текст, приложение не падает.
6. **`android/app/src/main/kotlin/.../ui/trackpad/TrackpadScreen.kt`** — минимальный трекпад:
   собирает `MotionEvent`, переводит dp в px по коэффициенту `densityDpi / 160`
   (`dx_px = dx_dp · densityDpi / 160 · sensitivity`), шлёт мышиный репорт не чаще 120 Гц.
   Порог тапа — сдвиг < 8 dp, порог drag — ≥ 8 dp; дельта больше 127 px в ветке A режется до 127
   и досылается вторым пакетом. Проверка: курсор на ПК двигается в ту же сторону, что палец; за 10 с
   движения нет залипаний (лог не содержит `sendReport failed`).

   Схема `DataStore`: Preferences, ключи `calib.h` (9 float через запятую), `calib.err5`, `calib.pz`,
   `calib.res`, `calib.ts`, `calib.schema` (текущая версия 1); несовпадение `schema` ⇒ инвалидация
   калибровки.
7. **`tools/hid_probe.py`** — скрипт на ПК на `hidapi` (Python-биндинг `hid`): перечисляет
   HID-устройства Windows и печатает markdown-таблицу с колонками
   `device / vid:pid / usage_page / boot / collections / verdict`; boot-протокол определяется по
   `usage_page = 0x01` и наличию `report_id` в дескрипторе. Проверка: запуск на каждом
   ПК матрицы даёт таблицу в `docs/measurement/hid-probe-<дата>.md`; повторный запуск воспроизводит её.
8. **`docs/measurement/phase0-report.md`** — протокол спайка: телефон, ПК, вердикт по профилю,
   задержка первого клика после 60 с idle, скриншот диспетчера устройств. Проверка: файл содержит
   заполненную строку на каждую из 6 пар «телефон × ПК» фазы 0 (5.2, матрица 5.5). Фаза 0 не
   закрывается, пока хотя бы одна строка пуста или помечена «не проверено».

### 5.4 План тестов

Три уровня. Юнит-тесты гоняются на JVM без телефона и без ПК, интеграционные — на реальном
Windows-ПК с реальным телефоном, полевые — руками по протоколу с записью чисел в CSV.
Порог «тест пройден» указан в каждой строке; тест без числового порога в план не входит.

#### 5.4.1 Юнит-тесты (`android/app/src/test/`)

| Тест | Что проверяет | Вход | Порог приёмки |
|---|---|---|---|
| `HomographySyntheticTest` | DLT + доводка Гаусса на 4 углах монитора | 4 соответствия «направление луча → точка», синтетика без шума | резидуум в углах < 0.01 px; обратное отображение возвращает исходные углы с ошибкой < 0.01 px |
| `HomographyNoiseTest` | устойчивость к шуму ориентации | тот же набор + шум 0.1° СКО, 100 прогонов | P90 ошибки в центре экрана ≤ 3.3 px (0.1° ≈ 3.3 px) |
| `HomographyDegenerateTest` | вырожденные конфигурации | три угла на одной прямой, два совпадающих угла | возвращается `CalibrationError.Degenerate`, коэффициенты не применяются |
| `OneEuroResponseTest` | отклик фильтра на ступеньку и на дрожание | ступенька 10°/с, затем покой с шумом 0.3°/с | профиль fast: выход достигает 90 % ступеньки за ≤ 60 мс; профиль precise: ≤ 200 мс; в покое амплитуда выхода < 0.5°/с |
| `OneEuroParamsTest` | дефолты из таблицы нормативов | fast (по умолчанию): `minCutoff=4.0`, `beta=0.02`; precise: `minCutoff=1.0`, `beta=0.007`; `dCutoff=1.0` | при beta=0 и частоте 100 Гц срез −3 дБ совпадает с `minCutoff` в пределах ±10 % |
| `DeadzoneTest` | мёртвая зона 0.5°/с | вход 0.3°/с и 0.7°/с | 0.3 → выход ровно 0; 0.7 → выход > 0 и масштаб сохраняется |
| `AccelCurveTest` | кривая ускорения `gain = 1 + a·k·(abs(ω)/ω_ref)^1.5` | вход 0.05, 5, 40 °/с при `a = 0.35` | выход монотонно растёт; на 40 °/с gain ≥ 3.0; на 5 °/с gain ≤ 1.15 |
| `PacketCodecRoundTripTest` | кодирование/декодирование всех типов пакетов | по 1000 случайных пакетов каждого типа, включая границы int8/int16 | 100 % байт-в-байт совпадение после round-trip; длины 6–10 байт |
| `PacketCodecVersionTest` | отказ на чужой версии | первый байт 0x02 и 0x00 | декодер возвращает `UnsupportedVersion`, не бросает исключение, соединение переводится в `degraded` |
| `SessionFsmTest` | все переходы FSM | `idle → discovering → connected → handshake → calibrating → active → degraded` + обрывы на каждом шаге | 100 % разрешённых переходов приняты, 100 % неразрешённых отклонены; из любого состояния есть путь в `idle` |
| `NoOpAfterPauseTest` | no-op пакет после паузы | пауза > 2 с, затем клик | первым в потоке уходит no-op, клик не теряется (проверяется на моке транспорта) |

#### 5.4.2 Интеграционные тесты (реальный Windows-ПК + реальный телефон)

| Тест | Сценарий | Порог приёмки |
|---|---|---|
| `hid_cursor_move` | движение пальца по трекпаду 10 с | курсор проходит ≥ 95 % заявленной дистанции; направление совпадает на 8/8 попытках |
| `hid_click` | одиночный тап, двойной тап, drag | 30/30 кликов доходят до цели; drag не отпускает кнопку раньше пальца |
| `hid_latin_input` | ввод «hello world 123» в Блокнот | посимвольно совпадает; ни одного лишнего символа на 3 попытках |
| `hid_wake_after_idle` | 60 с простоя, затем первый клик | первый клик доходит; задержка до курсора ≤ 50 мс (проверяется по видео 240 fps) |
| `agent_inject_click` | тот же набор через агент (RFCOMM) | 30/30 кликов; расхождение координат с целью ≤ 1 px |

### 5.7 Открытые вопросы к заказчику

Решённые вопросы сняты с обсуждения и перенесены в нормативы: минимальная версия Android — 28
(HID доступен с 28); основной режим — агент, если он доступен, HID — «режим без установки»;
Wi-Fi-транспорт — вне v1; магнетизм включён по умолчанию (радиус 60 px). Осталось четыре вопроса,
и только они блокируют планирование.

1. **В какие сроки делается L2 (ARCore) — v1.1 или позже?** Вариант A: v1.1 сразу после релиза v1,
   отдельной фазой (13 дней) и без блокировки релиза. Вариант B: позже, по спросу, только если
   устройства с ARCore окажутся у большинства пользователей. Последствие A: зависимость от наличия
   ARCore-устройства в матрице на всём сроке v1.1.
2. **Поддержка проектора как обязательного сценария?** Вариант A: обязательный сценарий — калибровка
   с предупреждением при `err₅` вне нормы, принудительный магнетизм, keystone-стенд в матрице
   (R13). Вариант B: best-effort — работает, но в приёмку и матрицу не входит.
3. **Арбитраж при двух подключённых телефонах.** Вариант A: второй телефон не подключается, пока
   активен первый (простое правило, но нужен явный экран отказа). Вариант B: оба подключаются,
   ввод идёт от последнего активного, переключение — с подтверждением в трее. Последствие B: новый
   набор тестов на переключение и риск «двух курсоров».
4. **Юридическая часть: лицензии и условия сторов.** ghostboard (MIT), ARCore, `uiautomation`,
   `pywinauto`, `bleak` — проверить совместимость и обязательные упоминания; условия Google Play
   для приложений, эмулирующих устройства ввода. Последствие: 2 дня работ и возможные правки
   листинга до релиза.

одного разработчика. L2 (фаза 5) идёт отдельной строкой вне этого пути: +20.4 дня, если заказчик
выбирает вариант «v1.1 сразу после релиза» (вопрос 5.7.1).
При двух разработчиках (Android + агент/алгоритмы) срок сжимается не вдвое: фазы 0, 2 и 5
требуют обе стороны, поэтому реальная экономия ≈ 30 % → **≈ 65–67 рабочих дней** (около 13 недель).

Чего в оценке нет и почему это названо прямо:

| Не входит | Последствие, если понадобится |
|---|---|
| iOS | Вне scope v1: нет публичного API быть HID-устройством |
| L3 (ZUPT-интеграл акселерометра) | Вне v1 (в сумму не входит): по брифу дрейф 8 см за 1 с и 34 см за 2 с; метрический объём из IMU не строится — это исследование, не задача |
| Метрики с магнитометром | `TYPE_GAME_ROTATION_VECTOR` выбран именно из-за вранья магнитометра у монитора; возврат к нему — переделка фильтра |
| Поддержка Linux/macOS-агента | Агент v1 — Windows: `SendInput`, UIA. Другие ОС — отдельный транспорт инъекции |
| Локализация интерфейса кроме русского и английского | Тексты вынесены в ресурсы, но перевод и вычитка — отдельные дни |

Ключевое ограничение срока: фазы 0 и 3 нельзя распараллелить с фазами 1–2 полностью — спайк
HID определяет, нужен ли агент как обязательный компонент (R1), а результаты фазы 3 определяют,
имеет ли смысл L2 (вопрос 5.7.1). Каждая из этих развилок может сдвинуть план на 1–2 недели,
поэтому буфер 20 % — минимум, а не запас.
