# Замер задержки Bluetooth-HID (20.11.2026)

Инструмент: `tools/hid_latency.py` (RAWINPUT на стороне Windows). Телефон подключён как HID
(`BTHENUM\{00001124…}_VID&000100e0_PID&0000`), схема питания «Сбалансированная»,
энергосбережение у HID-устройства уже снято, USB selective suspend — запрещён в настройках,
но до перезагрузки не применён (uptime 57 ч).

## Прогон 1 — «поводи, пауза, поводи» (`latency-before-reboot.csv`)

1198 отчётов движения, 24,8 с движения, 603 интервала.

| Интервал | Доля |
|---|---|
| 9–16 мс | 64,3 % |
| 17–32 мс | 14,4 % |
| 33–64 мс | 14,9 % |
| 65–128 мс | 2,8 % |
| 129–1000 мс | 3,3 % |

Медиана 16 мс, p95 78 мс, p99 344 мс. Пачек (интервал ≤ 2 мс) — 0 %.
Один интервал 2938 мс — это пауза руки, а не канал; инструмент тогда ошибочно назвал его
пробуждением из sniff (исправлено: интервалы > 1000 мс считаются паузой).

## Прогон 2 — непрерывное движение по кругу (`latency-continuous.csv`)

1502 отчёта, 1486 с движением, 592 активных интервала, 30 с.

- медиана **16 мс** → телефон шлёт ≈ **62 Гц** (канал умеет 125);
- p95 **63 мс**, p99 **203 мс**, максимум **672 мс** при непрерывном движении пальца;
- провалов 50–1000 мс: **91 из 592 = 15 %**;
- пачек нет: 0 % интервалов ≤ 2 мс.

## Ключевой вывод: движение теряется, а не запаздывает

| Отчёт | Средний шаг курсора |
|---|---|
| после обычного интервала (n=1239) | 10,7 |
| после провала 50–1000 мс (n=91) | 10,5 |

Отношение **0,99×**. Если бы отчёты копились в очереди и уходили позже, отчёт после провала
нёс бы накопленную дельту в 2–10 раз больше (с потолком на отчёт). Он несёт обычную —
значит за время провала движение просто не доехало: курсор недоезжает, а не дёргается позже.

Провалы распределены ровно по времени (3–7 в секунду, без сгустков) — это не один плохой
момент и не «соседний Wi-Fi на секунду заглушил».

## Что осталось различить

Два кандидата, оба дают такую картину:

1. **телефон не генерирует тик** — жест-машина на главном потоке, пропущенный кадр = потерянная дельта;
2. **отчёты теряются/задерживаются в радио** — но ACL в BR/EDR надёжный, с ретрансмиссией,
   поэтому потеря 15 % маловероятна; к тому же тогда копился бы backlog и появлялись пачки.

Решает одно число с телефона: экран связи → «Отправлено отчётов» до и после 30 с непрерывного
круга. При 62 Гц телефон должен выпустить ≈ 1860 отчётов.

- прирост ≈ 1860 при 1486 принятых на ПК → теряет радио;
- прирост ≈ 1486 → телефон отправляет ровно то, что доходит, и виноват его собственный тик
  (62 Гц с провалами) — лечится только на стороне приложения.

## Нормативы для сравнения

медиана ≤ 12 мс, p95 ≤ 35 мс, провалов 50–1000 мс ≤ 5 %. Сейчас: 16 / 63 / 15 %.
